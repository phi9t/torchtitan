* What This File Proves

This is a source-grounded, executable note for
[[https://github.com/pytorch/torchtitan/issues/1554][TorchTitan issue 1554]]. The issue asks why the visible transformation order is
=PP -> TP -> AC -> Compile -> FSDP/DDP=, and whether that order can be changed.

The short answer is that TorchTitan has two related ordering layers:

- Transformation order. Pipeline parallelism splits the model first. Inside
  each resulting model part, Llama3 then applies SPMD/TP work, async TP
  enablement, activation checkpointing, compile, and finally FSDP/HSDP.
- Rank and mesh layout. =ParallelDims= builds named mesh views from a global
  world mesh. In the full-DTensor dense view, the axes are
  =(pp, dp_replicate, dp_shard, cp, tp)=, so =pp= is the outer view axis and
  =tp= is the inner dense axis.

The executable blocks use the =torchtitan-rootfs= Jupyter kernel. They record
the live rootfs environment, the =ParallelDims= object, the custom Torch library
paths, the =llama3/parallelize.py= call order, and a post-config Llama3 model
plus device-mesh rendering.

All =jupyter-python= blocks share one kernel session. Earlier blocks create
objects such as =pd=, and later blocks inspect those same objects, so the file
acts like a recorded REPL session rather than a pile of disconnected snippets.
The shared session is declared once in the file-level header args above:
=:session /jpy:127.0.0.1#8899:torchtitan-parallelism-layout=. Individual
blocks stay small and rely on that session state.

* Issue 1554 Question

The issue body says:

#+begin_quote
Based on the code, the ordering of parallelization and optimization appears to
be: PP -> TP -> AC -> Compile -> FSDP/DDP.
Is it possible to modify this ordering? If not, could you explain the rationale
for this specific sequence?
#+end_quote

The issue discussion gives the informal maintainer rationale:

- =PP -> SPMD=: splitting pipeline stages first gives "clean SPMD regions".
  A later comment sharpens this: if a model is constructed stage-locally, the
  non-local layers do not exist, so PP has to happen before per-stage SPMD work.
- =TP -> FSDP=: the transformation order is natural because training iteration
  semantics run in the reverse direction.
- =TP -> AC=: reversing AC and TP has hit mixed =torch.Tensor= and =DTensor=
  failures after backward, so the current order is a working composition
  constraint, though the comment does not present it as fundamental.
- =AC -> torch.compile=: compile wrapping AC lets the compiler see the AC region
  when partitioning. AC wrapping compile risks repeated recomputation.
- =torch.compile -> FSDP=: compile can graph-break on FSDP2-wrapped modules.

The same thread says the ordering is still partly informal because MoE/EP and
PyTorch-side work such as =FSDP(AC)= and =SAC(compile)= are still changing the
supported composition space.

* TorchTitan Source Map

** Transformation Order

The source-backed control flow is:

- [[file:../../torchtitan/trainer.py::if parallel_dims.pp_enabled][trainer.py]] branches on pipeline parallelism first.
  - With PP enabled, it calls the model spec's =pipelining_fn= and passes
    =parallelize_fn= into that pipeline builder.
  - With PP disabled, it calls =parallelize_fn= directly.
- [[file:../../torchtitan/distributed/pipeline_parallel.py::def pipeline_llm][pipeline_llm]]
  obtains =pp_mesh=, splits the model into stages, then applies the model
  specific =parallelize_fn= to each stage-model chunk.
- [[file:../../torchtitan/models/llama3/parallelize.py::def parallelize_llama][parallelize_llama]]
  applies the non-pipeline SPMD work, then async TP enablement, activation
  checkpointing, compile, and finally FSDP/HSDP.
- [[file:../../torchtitan/models/qwen3/parallelize.py::def parallelize_qwen3][parallelize_qwen3]]
  follows the same shape, with an additional =skip_dp= path for inference.
- [[file:../../torchtitan/distributed/context_parallel.py::Must be called **before** ``Module.parallelize()``][context_parallel.py]]
  documents the legacy CP constraint: CP wrapping must happen before
  =Module.parallelize()= so CP logic runs inside the =local_map= boundary.
- [[file:../../torchtitan/distributed/fsdp.py::def apply_fsdp_to_decoder][apply_fsdp_to_decoder]]
  is the final data-parallel wrapper. It applies =fully_shard= to embeddings,
  transformer blocks, and finally the decoder root.

** Mesh Layout

=ParallelDims= owns the dimensional vocabulary and the mesh-view construction:

- [[file:../../torchtitan/distributed/parallel_dims.py::class ParallelDims][ParallelDims]]
  names =dp_replicate=, =dp_shard=, =cp=, =tp=, =pp=, =ep=, and =world_size=.
- [[file:../../torchtitan/distributed/parallel_dims.py::assert dp_replicate * dp_shard * cp * tp * pp == self.world_size][ParallelDims._validate]]
  checks =world_size = dp_replicate * dp_shard * cp * tp * pp=.
- [[file:../../torchtitan/config/configs.py::Expert parallelism degree][ParallelismConfig.expert_parallel_degree]]
  explains why =ep= is not multiplied directly into that dense formula:
  dense and sparse regions cover the same ranks, with
  =dp_shard * cp * tp == efsdp * ep= and
  =efsdp = dp_shard * cp * tp / ep=.
- [[file:../../torchtitan/distributed/parallel_dims.py::This API performs the following unflatten operations][ParallelDims.build_mesh]]
  derives several named views from the one-dimensional =("world",)= mesh.

The named views this checkout builds are:

- dataloading: =("pp", "batch", "cp", "tp")=
- full-DTensor dense storage: =("pp", "dp_replicate", "dp_shard", "cp", "tp")=
- legacy dense storage: =("pp", "dp_replicate", "fsdp", "tp")=
- SPMD-type forward/backward dense view: =("pp", "dp", "cp", "tp")=
- sparse MoE storage: =("pp", "dp_replicate", "efsdp", "ep")=

[[file:../../torchtitan/distributed/full_dtensor.py::_DENSE_STORAGE_AXES][full_dtensor.py]]
then names the SPMD storage-axis subsets as =["dp_replicate", "dp_shard", "cp", "tp"]=
for dense parameters and =["dp_replicate", "efsdp", "ep"]= for sparse MoE
parameters. [[file:../../torchtitan/models/README.md::canonical outer-to-inner SPMD order][models/README.md]]
calls those the canonical outer-to-inner SPMD orders for model authors.

** Megatron-Core Contrast

Megatron-Core answers a different but related question: how global ranks are
generated for process groups. A local first-party checkout at
=/data02/home/philip.yang/workspace/megatronlm= shows:

- =megatron.core.parallel_state.generate_masked_orthogonal_rank_groups=
  defines the rank mapping math. Its docstring gives
  =global_rank = tp_rank + dp_rank * tp_size + pp_rank * tp_size * dp_size=
  for a =tp-dp-pp= order, and the implementation generalizes that through
  prefix products.
- =RankGenerator= accepts =tp=, =ep=, =dp=, =pp=, =cp=, and =order=. Its default
  initialization path uses =order="tp-cp-ep-dp-pp"=.
- The default dense decoder rank generator uses =ep=1= and
  =cp=context_parallel_size=. The expert rank generator uses =cp=1= and
  =ep=expert_model_parallel_size=. =RankGenerator= asserts that CP and EP are
  not both greater than one in the same generator.
- The training config has an explicit switch, =use_tp_pp_dp_mapping=, that
  changes order from =tp-cp-ep-dp-pp= to =tp-cp-ep-pp-dp=.

The comparison point is that Megatron exposes a rank-order string to its rank
generator, while TorchTitan's primary source of truth is a set of named
=DeviceMesh= views plus a transformation order in trainer/model code.

** Correction To The Pasted Summary

For Megatron-Core, the common intuition that =tp= is fastest in the default
rank order is source-grounded. The default order string is
=tp-cp-ep-dp-pp=, and the rank formula is prefix-product based.

For this TorchTitan checkout, the statement "TorchTitan constructs a single
=("dp", "pp", "cp", "tp")= mesh" is not what the source says. TorchTitan first
creates a one-dimensional =("world",)= mesh, then derives named views from it.
The unflatten tuples put =pp= first and =tp= last for the dense views. The
SPMD-facing dense storage axes used by model sharding are
=(dp_replicate, dp_shard, cp, tp)=, while sparse MoE parameters use
=(dp_replicate, efsdp, ep)=.

Issue 1554 is therefore about two layers at once:

- transformation composition order: =PP -> SPMD/TP/CP/EP -> AC -> Compile -> FSDP=
- process-group and mesh layout: named mesh views with =pp= as the outer view
  axis and =tp= as the inner dense axis in the full-DTensor and SPMD layouts

Changing the former is a semantic/compiler/FSDP compatibility question. Changing
the latter is a rank placement and process-group construction question. They are
related because every transformation consumes a mesh view, but they are not the
same knob in this checkout.

* Llama3 Parallelize File Deconstruction

The file [[file:../../torchtitan/models/llama3/parallelize.py][torchtitan/models/llama3/parallelize.py]] is small enough to read as a
composition boundary. Its preamble imports three kinds of things:

- config types and dtype policy: =CompileConfig=, =ParallelismConfig=,
  =TrainingConfig=, and =TORCH_DTYPE_MAP=
- distributed transforms and mesh helpers: =ParallelDims=,
  =apply_cp_to_forward=, =maybe_enable_async_tp=, =apply_compile=,
  =resolve_fsdp_mesh=, =validate_config=, and =apply_fsdp_to_decoder=
- the model type being transformed: =Llama3Model=

The implementation has two branches. The modern =full_dtensor= and
=spmd_types= branch validates the model/config pair and delegates the local
state/input/output placement work to =model.parallelize(parallel_dims)=. The
legacy branch applies CP directly to attention kernels first, then calls the
same =model.parallelize= hook only for TP.

If we erase the compatibility branches and write only the clean full-DTensor
case, the transformation reads as a straight pipeline:

#+begin_src python
validate_config(parallel_dims, model)
model.parallelize(parallel_dims)
maybe_enable_async_tp(parallelism, compile_config, parallel_dims.get_mesh("tp"))
ac_config.build(dump_folder=dump_folder).apply(model)
apply_compile(model, compile_config)
dp_mesh, dp_mesh_dims = resolve_fsdp_mesh(parallel_dims)
apply_fsdp_to_decoder(
    model,
    dp_mesh,
    param_dtype=TORCH_DTYPE_MAP[training.mixed_precision_param],
    reduce_dtype=TORCH_DTYPE_MAP[training.mixed_precision_reduce],
    pp_enabled=parallel_dims.pp_enabled,
    cpu_offload=training.enable_cpu_offload,
    reshard_after_forward_policy=parallelism.fsdp_reshard_after_forward,
    dp_mesh_dims=dp_mesh_dims,
    enable_symm_mem=parallelism.enable_fsdp_symm_mem,
)
#+end_src

This is the order issue 1554 is really asking about inside a pipeline stage:
=SPMD model.parallelize -> async TP enablement -> AC -> compile -> FSDP/HSDP=.
The outer =PP -> stage-local parallelize_fn= edge lives in
[[file:../../torchtitan/distributed/pipeline_parallel.py::for i, m in enumerate(model_parts)][pipeline_llm]], not in
=llama3/parallelize.py= itself.

** Full-DTensor Command Deep Dive

The full-DTensor branch in
[[file:../../torchtitan/models/llama3/parallelize.py::43][parallelize_llama]]
is short, but each command sits on top of a fairly specific contract. Read it
as a model-local transformation pipeline that runs after pipeline splitting has
already decided which stage-local module this rank owns.

*** =validate_config(parallel_dims, model)=

The callsite is
[[file:../../torchtitan/models/llama3/parallelize.py::44][parallelize.py:44]].
The implementation lives at
[[file:../../torchtitan/distributed/full_dtensor.py::30][full_dtensor.py:30]].
It is intentionally narrow today: it walks the actual module tree and rejects
=full_dtensor= or =spmd_types= with CP when the model uses
=ScaledDotProductAttention= or =VarlenAttention=.

That means this is not the general shape validator for TP/DP/PP. It is a
compatibility guard for multi-axis SPMD backends. The important detail is that
it inspects the built model, not just the config, so it catches the attention
implementation that will actually run.

*** =model.parallelize(parallel_dims)=

The callsite is
[[file:../../torchtitan/models/llama3/parallelize.py::45][parallelize.py:45]].
The method it resolves to is the shared module protocol at
[[file:../../torchtitan/protocols/module.py::248][module.py:248]].

This call is the main SPMD/TP materialization step. It recursively descends
through =Module= children, and for each module carrying a =_sharding_config= it:

- distributes direct parameters and buffers according to =state_shardings=
- caches positional argument names from the module's =forward= signature
- optionally wraps local compute regions with =local_map=
- replaces =forward= with a wrapper that redistributes inputs, calls the local
  or DTensor-aware body, then redistributes outputs

For Llama3, the sharding metadata exists because the config update path seeds
it before model construction. =Llama3Model.Config.update_from_config= calls
[[file:../../torchtitan/models/llama3/sharding.py::25][set_llama3_sharding_config]]
through
[[file:../../torchtitan/models/llama3/model.py::83][model.py:83]]. That helper
fills the root decoder sharding and then walks every layer config.

Useful sub-contracts:

- [[file:../../torchtitan/models/common/decoder_sharding.py::272][decoder_sharding.py:272]]
  gives =tok_embeddings.weight= a dense parameter layout with TP sharding.
- [[file:../../torchtitan/models/common/decoder_sharding.py::174][decoder_sharding.py:174]]
  gives the attention module its input/output boundary layouts.
- [[file:../../torchtitan/models/common/decoder_sharding.py::186][decoder_sharding.py:186]]
  colwise-shards the QKV projection.
- [[file:../../torchtitan/models/common/decoder_sharding.py::187][decoder_sharding.py:187]]
  rowwise-shards the attention output projection.
- [[file:../../torchtitan/models/common/decoder_sharding.py::244][decoder_sharding.py:244]]
  declares the FFN boundary, and
  [[file:../../torchtitan/models/common/decoder_sharding.py::248][decoder_sharding.py:248]]
  through
  [[file:../../torchtitan/models/common/decoder_sharding.py::250][decoder_sharding.py:250]]
  apply colwise/rowwise layouts to =w1=, =w3=, and =w2=.

So the command name =model.parallelize= is compact, but it is not a single
tensor-parallel wrapper. It is the point where TorchTitan turns the model's
registered sharding intent into distributed state and module-boundary behavior.

*** =maybe_enable_async_tp(parallelism, compile_config, tp_mesh)=

The callsite is
[[file:../../torchtitan/models/llama3/parallelize.py::56][parallelize.py:56]],
guarded by =parallel_dims.tp_enabled=. The implementation is
[[file:../../torchtitan/distributed/tensor_parallel.py::102][tensor_parallel.py:102]].

This command is deliberately tiny. If async TP is disabled, it returns. If async
TP is enabled, it requires model-level compile to be enabled; otherwise it
raises. When the precondition is satisfied, it flips
=torch._inductor.config._micro_pipeline_tp = True=.

That explains why it sits after =model.parallelize= and before compile. The
model has already been transformed into TP-aware distributed structure, and the
compiler has not yet captured the transformer blocks. Async TP is therefore a
compiler/backend scheduling option for the already-TP model, not a replacement
for the model sharding pass.

*** =ac_config.build(...).apply(model)=

The callsite is
[[file:../../torchtitan/models/llama3/parallelize.py::62][parallelize.py:62]].
The shared =apply= method for the ordinary AC policies is
[[file:../../torchtitan/distributed/activation_checkpoint.py::152][activation_checkpoint.py:152]].

The ordinary AC path disables the Dynamo LRU cache, obtains =model.layers=, and
wraps each transformer block. The concrete wrapper depends on the selected
config:

- =FullAC= wraps the entire transformer block with PyTorch's checkpoint wrapper
  at
  [[file:../../torchtitan/distributed/activation_checkpoint.py::173][activation_checkpoint.py:173]].
- =SelectiveAC= builds a custom checkpoint policy at
  [[file:../../torchtitan/distributed/activation_checkpoint.py::214][activation_checkpoint.py:214]]
  and chooses which ops to save versus recompute.
- =MemoryBudgetAC= does not wrap each layer in the same way; its =apply= at
  [[file:../../torchtitan/distributed/activation_checkpoint.py::315][activation_checkpoint.py:315]]
  configures the compiler partitioner memory budget.

The practical reason this comes before compile is visible in the next command:
TorchTitan compiles each transformer block after AC wrapping, so the compiler
sees the AC-shaped block boundary.

*** =apply_compile(model, compile_config)=

The callsite is
[[file:../../torchtitan/models/llama3/parallelize.py::67][parallelize.py:67]],
guarded by =compile_config.enable= and ="model" in compile_config.components=.
The implementation is
[[file:../../torchtitan/distributed/compile.py::35][compile.py:35]].

This is regional model compile, not whole-model compile. It sets Dynamo flags
needed by the current model stack, resolves the backend, then iterates
=model.layers.named_children()= and calls =transformer_block.compile(...)= with
=fullgraph=True=.

Two details matter for the ordering question:

- The source comment at
  [[file:../../torchtitan/models/llama3/parallelize.py::65][parallelize.py:65]]
  says this is "after AC wrapping and before FSDP".
- The compile helper has a special =aot_eager= path for models using
  =FlexAttention=: [[file:../../torchtitan/distributed/compile.py::61][compile.py:61]]
  wraps the backend so FlexAttention regions can still be lowered through
  inductor.

The command is therefore placed where the module still looks like a stack of
transformer blocks, but after the AC policy has changed the block bodies.

*** =resolve_fsdp_mesh(parallel_dims)=

The callsite is
[[file:../../torchtitan/models/llama3/parallelize.py::72][parallelize.py:72]].
The implementation is
[[file:../../torchtitan/distributed/full_dtensor.py::70][full_dtensor.py:70]].

This command selects the dense storage mesh and the explicit FSDP data-parallel
axes. For =full_dtensor=, the dense storage axes are
=dp_replicate, dp_shard, cp, tp= at
[[file:../../torchtitan/distributed/full_dtensor.py::54][full_dtensor.py:54]].
=resolve_fsdp_mesh= asks =ParallelDims= for the activated mesh over those axes,
then builds a =DataParallelMeshDims= where:

- =dp_shard= is always the shard axis
- =cp= joins the shard axes when CP is enabled
- =dp_replicate= is the replicate axis when HSDP replication is enabled

This is where the dense full-DTensor layout becomes an FSDP input contract.
The backing mesh view is constructed in
[[file:../../torchtitan/distributed/parallel_dims.py::286][parallel_dims.py:286]]
through
[[file:../../torchtitan/distributed/parallel_dims.py::296][parallel_dims.py:296]]
as =("pp", "dp_replicate", "dp_shard", "cp", "tp")=.

*** =apply_fsdp_to_decoder(...)=

The callsite is
[[file:../../torchtitan/models/llama3/parallelize.py::80][parallelize.py:80]].
The implementation is
[[file:../../torchtitan/distributed/fsdp.py::110][fsdp.py:110]].

This command installs FSDP2/HSDP on a decoder-style model. It constructs a
=MixedPrecisionPolicy= from the training dtypes, carries the explicit
=dp_mesh_dims= from =resolve_fsdp_mesh=, applies optional CPU offload, resolves
the =reshard_after_forward= policy, and then wraps:

- token embeddings, root norm, and LM head at
  [[file:../../torchtitan/distributed/fsdp.py::180][fsdp.py:180]]
  through
  [[file:../../torchtitan/distributed/fsdp.py::207][fsdp.py:207]]
- every transformer block at
  [[file:../../torchtitan/distributed/fsdp.py::209][fsdp.py:209]]
  through
  [[file:../../torchtitan/distributed/fsdp.py::308][fsdp.py:308]]
- the decoder root itself at
  [[file:../../torchtitan/distributed/fsdp.py::310][fsdp.py:310]]

For dense Llama3, the MoE-specific branches are skipped. If =dp_replicate= is
present in the mesh names, the result is logged as HSDP; otherwise it is pure
FSDP. The function also disables FSDP's automatic gradient division at
[[file:../../torchtitan/distributed/fsdp.py::315][fsdp.py:315]], because
TorchTitan handles gradient scaling in the training loop.

def _layout_axes(layout):
    if layout is None:
        return "-"
    return "(" + ", ".join(axis.value for axis in layout.axes()) + ")"

def _module_sharding_summary(name, module):
    sharding = getattr(module, "_sharding_config", None)
    if sharding is None:
        return f"{name}: no sharding_config"
    state = ", ".join(
        f"{param}:{_layout_axes(layout)}"
        for param, layout in sharding.state_shardings.items()
    ) or "no direct state"
    inputs = ", ".join(
        f"{arg}:{_layout_axes(layout)}"
        for arg, layout in (sharding.in_src_shardings or {}).items()
    ) or "no input boundary"
    output = _layout_axes(sharding.out_dst_shardings)
    return f"{name}: state[{state}] in[{inputs}] out[{output}]"

def _dense_mesh_lines(parallel_dims):
    shape = (
        parallel_dims.pp,
        parallel_dims.dp_replicate,
        parallel_dims.dp_shard,
        parallel_dims.cp,
        parallel_dims.tp,
    )
    rank = 0
    lines = []
    for pp_i in range(shape[0]):
        for dpr_i in range(shape[1]):
            for dps_i in range(shape[2]):
                for cp_i in range(shape[3]):
                    tp_ranks = list(range(rank, rank + shape[4]))
                    rank += shape[4]
                    lines.append(
                        f"pp{pp_i} dp_replicate{dpr_i} "
                        f"dp_shard{dps_i} cp{cp_i} -> tp ranks {tp_ranks}"
                    )
    return lines

def _dense_device_mesh(parallel_dims):
    mesh_tensor = torch.arange(parallel_dims.world_size).reshape(
        parallel_dims.pp,
        parallel_dims.dp_replicate,
        parallel_dims.dp_shard,
        parallel_dims.cp,
        parallel_dims.tp,
    )
    return DeviceMesh(
        "cuda",
        mesh_tensor,
        mesh_dim_names=("pp", "dp_replicate", "dp_shard", "cp", "tp"),
        _init_backend=False,
        _rank=0,
    )
