## 0. Headline

- **320B-A18B is accurate.** Exact count from shard headers: 321,323,031,390
  parameters (matches the HF API `safetensors.total`). Text decoder without MTP
  and vision: 313.33B total, **17.38B active per token** (Section 1.6).
- **45 decoder layers, 3:1 KDA:sparse.** Layers 3, 7, 11, ..., 43 (11 layers)
  are NoPE MLA with a DeepSeek-style sparse indexer ("DSA"); the other 34 are
  Kimi Delta Attention (KDA). One MTP layer (index 45) is DSA + MoE. Every layer
  uses 4-stream mHC residuals. **No RoPE anywhere in the text model.**
- **MoE:** 288 routed experts, top-8, 1 shared expert, sigmoid router with
  correction bias, first 3 layers dense.
- **Weights are downloadable** (MIT, not gated) as block-FP8 (328 GB) and as a
  separate BF16 repo (643 GB). The model is natively multimodal (24-layer ViT,
  0.56B).
- **4x vs 8x B200, LoRA SFT:** 8x fits comfortably with BF16 frozen base at 8k
  and fits 32k with full activation checkpointing. 4x is marginal: BF16 base
  alone is 146 GiB/GPU, leaving about 20 GiB, enough only for about 8k tokens
  per rank with full AC and chunked loss; anything longer on 4x needs an
  FP8-stored frozen base or CP for the sparse layers, neither of which exists in
  this checkout.

### 1.2 Per-layer schedule

From `layer_types`, `mlp_layer_types`, `linear_attn_config.kda_layers` /
`full_attn_layers`, and `indexer_types`:

```text
layer:  0 1 2 3 4 5 6 7 8 ... 40 41 42 43 44 | 45 (MTP)
attn:   K K K S K K K S K ...  K  K  K  S  K |  S
mlp:    D D D M M M M M M ...  M  M  M  M  M |  M

S = NoPE MLA + own indexer (11 layers: 3,7,11,15,19,23,27,31,35,39,43)
```

(`indexer_types` all `"full"`).

### 1.5 MTP, vision, tokenizer, chat format

- **MTP** (`layers.45`): `enorm`, `hnorm`, `eh_proj` [4096, 8192],
  `shared_head.norm`, sparse MLA + indexer, MoE; shares embeddings and
  `lm_head`; no mHC tensors (45 `hc_*` sets for 46 layers; vLLM skips mHC on
  the MTP layer, `vLLM:common/model.py:442`). HF ignores it on load
  (`_keys_to_ignore_on_load_unexpected`, `HF:1378`).
- **Vision**: `vision_config` depth 24, hidden 1024, 16 heads, patch 14,
  temporal patch 2, spatial merge 2, merger to 4096 (563.6M params). Image token
  id 154854, video 154855.
- **Tokenizer**: `tokenizer.json` (20 MB, `backend: tokenizers`); special tokens
  include `[gMASK]`, `<sop>`, `<|system|>`, `<|user|>`, `<|assistant|>`,
  `<|observation|>`. `eos_token_id: [154820, 154827, 154829]`,
  `pad_token_id: 154820`; generation defaults `temperature 1.0, top_p 0.95`.
- **Chat template / reasoning**: prompt starts `[gMASK]<sop>`, then a system
  line `Reasoning Effort: Max|High|Low` (`reasoning_effort` in {low, high},
  default max). Assistant turns render `<think>...</think>` then content;
  generation prompt is `<|assistant|><think>`. `clear_thinking` defaults to
  **false**, i.e. prior turns keep their reasoning (interleaved thinking); the
  card says to pass `clear_thinking=true` for chat. Tool calls use
  `<tool_call>name<arg_key>k</arg_key><arg_value>v</arg_value></tool_call>`
  and tool results go under `<|observation|>`. SFT data must be rendered with
  this exact template, including the `clear_thinking` choice.

## 2. Mechanism deep dive

Notation: T tokens, D = 4096, H = heads, P = number of pools.

### 2.1 Decoder layer with mHC (`HF:1278-1348`, `HF:218-336`)

```text
h: [T, 4, D]   (embedding copied into 4 streams, HF:1493)
attn_hc(h):   flat = rms_unweighted(h.view(T, 4D).float())          # HF:300-301
              m = flat @ hc_attn_fn^T                               # [T, 24]
              pre  = sigmoid(m[:4]*s0 + b[:4]) + 1e-6               # [T, 4]
              post = 2*sigmoid(m[4:8]*s1 + b[4:8])                  # [T, 4]
              comb = softmax(m[8:].view(4,4)*s2 + b, -1) + 1e-6
              comb = col_norm(comb); repeat 19x (row_norm, col_norm) # Sinkhorn, HF:315-324
              x = sum_i pre_i * h_i                                 # [T, D]
x = input_layernorm(x); y = attn(x)
h' = post[..., None] * y[:, None, :] + comb^T @ h                   # HF:1335-1337
(same again with ffn_hc / post_attention_layernorm / mlp)
final: norm(mean over the 4 streams)                                # HF:332-336, 1509
```

The final collapse is an **unweighted mean**, explicitly "Unlike DeepSeek-V4"
(`HF:333`). The checkpoint therefore has no `hc_head` tensors.

### 2.2 Indexer (`HF:772-913`)

Per sparse layer, with `q_resid = q_a_layernorm(q_a_proj(x))` [T, 1536]
shared with MLA:

```text
q_idx   = wq_b(q_resid).view(T, 32, 128)
k_tok   = LayerNorm(wk(x))                     # [T, 128], one key head
g_tok   = x @ index_kpool_compress_gate^T      # [T, 128]
k_pool  = IndexPool(k_tok, g_tok)              # [P, 128], P = ceil(T/4)
s[t,p]  = sum_h w[t,h] * relu(q_idx[t,h] . k_pool[p] * 128^-0.5)
          with w = weights_proj(x) * 32^-0.5    # [T, 32]
valid   = pool p complete AND its last token <= t
top     = topk(s, 2048 / 4 = 512 pools)         # torch.topk, HF:888
idx     = expand each pool to its 4 raw tokens  # [T, 2048]
        + tail: raw tokens of the current incomplete pool (0..3 tokens)
        -> int32 [T, 2051], -1 padded           # HF:902-913
```

The whole HF indexer forward is decorated `@torch.no_grad()` (`HF:809`): the
reference implementation gives the indexer no gradient. vLLM computes the same
selection with FP8 MQA logits after a Hadamard-128 rotation of q and pooled k
(`vLLM:common/attention.py:344-351`,
`vLLM:nvidia/ops/kpool_compress.py:39-48`); the rotation is orthogonal so
the ranking is unchanged in exact arithmetic, but FP8 quantization is a
trainer/generator mismatch source for RL (Section 6).

### 2.3 IndexPool exactly as implemented (`HF:935-1008`, `vLLM:nvidia/ops/kpool_compress.py:141-230`)

```text
pools are non-overlapping groups of 4 consecutive tokens, anchored at the
first valid (non-padding) token of the sequence (HF:976-983)
logits[p, j, c] = g_tok[4p+j, c] + ape[j, c]           # j in 0..3, c in 0..127
prob[p, :, c]   = softmax_j(logits[p, :, c])          # per-channel softmax over the 4 slots
k_pool[p, c]    = sum_j prob[p, j, c] * k_tok[4p+j, c]
pool valid only if all 4 slots valid; incomplete tail pool is never scored
```

No normalization after pooling, no RoPE, no overlap with the previous pool.
vLLM stores one pooled FP8 entry per 4 tokens in the indexer cache plus a
paged tail buffer for the in-progress pool (`vLLM:common/attention.py:79-170`).
Initialization in HF is `ape = 0`, `gate = 1` (`HF:1418-1420`).

### 2.4 KDA (`HF:339-393`, `HF:463-614`, `HF:620-769`)

```text
qkv  = SiLU(causal_conv4([q_proj x, k_proj x, v_proj x]))   # each [T, 64, 128]
q, k = l2norm(q), l2norm(k)                                # fp32, eps 1e-6
beta = sigmoid(b_proj x)                                   # [T, 64]
g    = -5 * sigmoid(exp(A_log)[h] * (f_b(f_a(x)) + dt_bias))   # [T, 64, 128], in (-5, 0)
recurrence per head (S: [128, 128] fp32):
  S_t = diag(exp(g_t)) S_{t-1}
  S_t = S_t + k_t (beta_t (v_t - S_t^T k_t))^T              # delta rule
  o_t = S_t^T (q_t / sqrt(128))
out  = o_proj(RMSNormGated(o, gate = g_b(g_a(x)), act = sigmoid))
```

The bounded gate is selected because `gate_lower_bound` is set
(`HF:351-363`); vLLM uses `chunk_kda_with_fused_gate(..., safe_gate=True)`
with the same formula (`vLLM:common/kda.py:335-350`, `:402-403`). Chunked
form (`HF:516-614`): chunk size 64, cumulative log-decay per channel within a
chunk, UT-transform via the lower-triangular solve (`HF:568-577`), then
inter-chunk state propagation `S <- S*exp(g_last) + (k*exp(g_last - g))^T v_new`
(`HF:602-605`). State per layer per sequence: 64 x 128 x 128 fp32 = 4 MiB.

### 2.5 How sparse MLA consumes indices (`HF:1174-1275`)

HF expands the latent to full K/V (`expand_kv`, `HF:1155-1172`), converts
`[T, 2051]` indices into a dense boolean mask `[B, 1, T, T]`
(`build_attention_mask_from_topk`, `HF:1237-1275`) and runs SDPA. That is a
correctness reference only: `_supports_flash_attn = False`,
`_supports_flex_attn = False` (`HF:1357-1361`). vLLM runs NoPE sparse MLA in
the absorbed latent space (FlashMLA/FlashInfer sparse MLA; PRs #55385,
#55277).

There is **no attention sink and no sliding window** in GLM-5.3-Flash's
attention; the "tail" (up to 3 most recent raw tokens of the incomplete pool)
is the only local component. For T <= 2051 every causal token is selected, so
sparse attention is exactly dense causal attention on short sequences.

### 3.2 Indexer training-time behaviour: DSv4 in repo vs GLM-5.3-Flash

- Repo DSv4: the indexer receives `x.detach()` and `qr.detach()`
  (`deepseek_v4/attention.py:341-344`) and the auxiliary indexer loss is
  "intentionally dropped for now" (`:54-56`). Its parameters therefore get
  **no gradient**: the indexer is effectively frozen.
- GLM-5.3-Flash HF reference: indexer forward is `@torch.no_grad()`
  (`HF:809`), also frozen.
- GLM-5 report: the indexer is trained with a dense warmup (1,000 steps) and
  then a sparse adaptation stage (Section 2.1.1), and "We also freeze the
  indexer parameters by default during RL to accelerate training and prevent
  unstable learning in the indexer" (Section 3.2). The report says nothing
  about SFT. It also states "adopting a deterministic top-k operator
  effectively resolves the training-inference mismatch" and uses `torch.topk`
  in RL ([arXiv:2602.15763](https://arxiv.org/html/2602.15763)).
- Conclusion: for SFT and RL the repo's DSv4 behaviour (frozen, detached
  indexer) **matches** what Z.ai does in RL and what the HF reference does.
  Training the indexer would need the KL loss from upstream
  [pytorch/torchtitan#4835](https://github.com/pytorch/torchtitan/pull/4835)
  ("[Deepseek V4] Dsv4 sparse indexer loss", merged 2026-10-12): it adds
  `SparseIndexerLoss(AuxLoss)`, makes `Indexer.select` return differentiable
  `topk_scores`, and uses attention LSE as the detached teacher. It is **not
  in this checkout** (no `SparseIndexerLoss` symbol), though the `AuxLoss`
  framework it builds on is (`torchtitan/models/common/aux_loss.py`). Relevant
  only for long-context continued pretraining, not for the cheapest SFT path.

### 3.3 Seam

Put the model in a new core model folder `torchtitan/models/glm5_next/`
(`flavors.py`, `model.py`, `sharding.py`, `state_dict_adapter.py`), following
`.claude/rules/models.md`. It is a released public checkpoint built from core
components (KDA, sparse indexer, mHC, MoE), like `kimi_k3` and `deepseek_v4`.
The one GLM-specific kernel composition (pool-expanded raw-token gather
attention) belongs in that folder. Shared pieces that need generalizing
(two-linear output gate in `KDA`, `HcPost` axis, `HcHead` mean option, a
compressor without post-norm/rope) should be fixed in place, with all callers
(`kimi_k3`, `deepseek_v4`) re-verified, rather than copied. The training recipe
(LoRA transform, data, AC) goes in `torchtitan_recipes/models/glm5_next.py`.

### 3.4 Finding: DSv4 `HcPost` mixes the residual streams along the other axis

`deepseek_v4/mhc.py:142-144` computes, for folded inputs `[T, n, D]`:

```text
torch.sum(comb.unsqueeze(-1) * residual.unsqueeze(-2), dim=2)
= residual_i * sum_j comb[i, j]
```

GLM (`HF:1335-1337`) computes `comb^T @ residual`, i.e. `sum_i comb[i, j] *
residual_i`. With random tensors the two differ (`torch.allclose` is False),
while the same expression evaluated with an extra leading batch dimension
(the shape it was written for) equals the GLM form. The check ran inside the
rootfs on plain tensors; importing `torchtitan.models.deepseek_v4.mhc` failed
in the current rootfs (`ImportError: cannot import name 'SpmdType' from
'spmd_types'`), so the module itself was not executed. Treat this as a
**suspected DSv4 bug**. Confirm it with a unit test against the DeepSeek-V4
reference before relying on it; a GLM port must use `comb^T @ residual` in
either case.

## 4. Training-time concerns

- **Sparse-attention backward.** Available through Attention Gym
  `gather_attn` (pinned `attn-gym[linear,cudnn]==0.0.16`, `requirements.txt:11`).
  It has a Triton backward and a CuTe backward (CuTe requires head_dim 512 and
  shared KV, eager only; deterministic mode and `torch.compile` fall back to
  Triton; Triton shared-KV backward uses atomics unless deterministic
  algorithms are enabled). The indexer top-k needs no backward because the
  indexer is frozen. FlashMLA/DeepGEMM/cuDNN sparse kernels are inference-side
  (vLLM) only; cuDNN-frontend sparse indexer/attention is still an open design
  issue (#831). FlexAttention is not a practical fallback: GLM's selection is
  per-query arbitrary indices (HF disables flex for this reason, `HF:1360-1361`).
  The HF SDPA path is an O(T^2) dense-mask oracle.
- **KDA backward.** Yes: Attention Gym `chunk_kda` / `_ChunkKDA` / cuDNN
  `ChunkKdaCudnn` (imported at `torchtitan/models/common/attn_gym.py:33-43`),
  CuTe on SM100/SM103 and Triton elsewhere (`kimi_k3/README.md`). Kimi K3
  reports HF parity at KL 1.02e-5 (`kimi_k3/README.md:53-60`).
- **Indexer in SFT/LoRA.** Freeze it (do not target `indexer.*`), and keep it
  out of the optimizer. This matches the HF reference and the RL recipe, and
  with T <= 2051 the indexer has no effect at all.
- **Context parallel.** KDA: supported (`cp_kda.py`). DSv4 sparse attention:
  explicitly rejected, "Context Parallel is not yet supported for DeepSeek V4
  sparse attention." (`deepseek_v4/model.py:264-266`). For GLM, CP is
  tractable because the latent KV is only 512 x bf16 = 1 KiB per token per
  layer: all-gather the latent and the pooled indexer keys across CP, then run
  `lightning_indexer` + `gather_attn` locally with global indices. Not built.
- **Mixed dtype.** `training.dtype` is global (`torchtitan/config/configs.py:100-107`).
  The frozen base must be stored in bf16 to fit, but then LoRA weights and
  Adam states are bf16 too, and the fp32 checkpoint tensors (`A_log`,
  `dt_bias`, `e_score_correction_bias`, mHC `base/scale`) are rounded. The
  existing TODO points at per-FQN mixed precision
  (`kda.py:121-122`, pytorch/pytorch#156784).
- **Router during SFT.** Freeze `gate.weight` and `e_score_correction_bias`
  (no bias updates); LoRA on routed experts is possible (`get_lora_dist_moe_routed_experts`)
  but costs memory (Section 5).
- **Environment.** The current rootfs has vLLM 0.27.0, Transformers 5.15.0,
  no `attn_gym`, and a `spmd_types` that does not match the repo. vLLM's
  `vllm/models/glm5next/` exists at tag v0.30.0 (absent at v0.28.0/v0.29.0 by
  raw-path check; the vLLM recipe badge says 0.29.0+, possibly at an older
  path). Transformers needs >= 5.17.0.

RL budget: a generator needs the policy weights too. vLLM's own recipe uses
FP8 at TP4 ("About 306 GiB for the default FP8 checkpoint"; examples on a GB200

[recipes.vllm.ai](https://recipes.vllm.ai/zai-org/GLM-5.3-Flash)). A BF16
generator needs 8 GPUs. So 8 GPUs total (trainer 4 + generator 4) works only
if both sides hold FP8-stored weights; the realistic minimum for BF16 LoRA RL
is 8 trainer + 4 FP8 generator, i.e. 12-16 B200.

### 5.5 Storage (HDFS via waystone)

Model weights, datasets, and checkpoints live on HDFS under the waystone
layout, resolved with `waystone layout-profile --project torchtitan --json`
(`model_weights`, `datasets`, `checkpoints`; see
`/data02/home/philip.yang/workspace/waystone/docs/shared-hdfs-storage.md`).
Never hand-join the URI; use `waystone storage-prefix --child ...` or
`waystone.storage.hdfs_storage_path`.

TorchTitan cannot read the checkpoint directly from `hdfs://` today:

- `HuggingFaceStorageReader` extends `FileSystemReader` and opens shards
  with `safetensors.safe_open`, both local-filesystem only (rootfs
  `torch/distributed/checkpoint/hf_storage.py:202`).
- The base adapter reads `model.safetensors.index.json` with plain `open()`
  (`torchtitan/models/base/state_dict_adapter.py:141-143`), and the
  tokenizer loads from a local `hf_assets_path`.
- Only DCP-format checkpoint folders go through fsspec
  (`torchtitan/components/checkpointer/dcp.py:271-277`), and an `hdfs://`
  fsspec backend would still need the waystone libhdfs runtime.

So HF weights must be staged to local NVMe. Sizes: FP8 repo 306 GiB, BF16
repo 598 GiB. Local free space on this host: `/data05` 872 GB, `/opt` 409 GB,
`/data02` only 202 GB. The BF16 checkpoint fits only on `/data05`.

## 6. SFT and RL path

### 6.1 TorchTitan path

1. **Model folder** `torchtitan/models/glm5_next/` (text-only first; vision
   later via `torchtitan/models/common/vision_encoder.py`), composed from
   KDA, DSv4 indexer/`lightning_indexer`, a pool compressor, `gather_attn`
   raw-token sparse MLA, mHC with the GLM post-mix, and `common/moe.py`.
2. **State-dict adapter** from the BF16 repo:
   `model.language_model.layers.{i}.self_attn.{q,k,v}_proj` -> `delta_attention.{q,k,v}_proj`,
   `{q,k,v}_conv1d` -> `{q,k,v}_conv`, `f_a/f_b` -> `forget_a/forget_b`,
   `g_a/g_b` -> new `output_gate_a/b`, `b_proj` -> `beta`, `dt_bias` reshape
   [8192] <-> [64,128]; MLA `q_a_proj/q_b_proj/kv_a_proj_with_mqa/kv_b_proj/o_proj`
   -> `wq_a/wq_b/wkv_a/wkv_b/wo`; `indexer.*` one-to-one; `hc_{attn,ffn}_{fn,base,scale}`
   -> `hc_{attn,ffn}_pre.hc_{fn,base,scale}`; per-expert
   `mlp.experts.{e}.{gate,up,down}_proj` grouped via `moe_state_dict_adapter`;
   `mlp.gate.weight` / `e_score_correction_bias` -> router weight / expert
   bias. The FP8 repo additionally needs `from_quantized=True` with block 128
   (`deepseek_v3/state_dict_adapter.py:133-156`). Verify every key is consumed
   and the round trip `to_hf(from_hf(sd))` is bitwise.
3. **LoRA SFT**: `LoRATransform(rank=16, alpha=32, target_modules=[...attention and
   shared-expert projections...])` in a `torchtitan_recipes` config, full AC,
   chunked loss, `training.dtype=bfloat16` (or a per-FQN fp32 carve-out for
   LoRA params if built), indexer and router frozen.
4. **RL** (`torchtitan/rl/`, moved from `torchtitan/experiments/rl/` by
   commit `ec953b360`, "[RL] Share the core training engine (#4773)"; the
   CLAUDE.md paths are stale). TitanRL runs the **TorchTitan model inside
   vLLM** (registered as `TorchTitanCausalLM`,
   `torchtitan/rl/model/vllm_registry.py:39`). It does not use vLLM's native
   `glm5next`. The RL README model table lists DeepSeek V4 and Kimi K3 as
   "Support coming soon" (`torchtitan/rl/README.md:31-42`). The vLLM-side
   adapters cover paged KDA (`torchtitan/rl/model/kda.py:14-23`, with
   `bound_gate`) and dense varlen attention (`torchtitan/rl/model/attention.py`).
   There is no paged sparse-MLA + pooled-indexer cache adapter. So GLM RL in
   TitanRL needs: (a) a paged latent cache plus pooled indexer cache plus tail
   buffer in `rl/model/` (vLLM's `Glm5NextIndexerCache`/`Glm5NextTailCache`
   are the template, `vLLM:common/attention.py:79-170`); (b) KDA decode reuse;
   (c) an mHC-aware decoder. vLLM version: `scripts/install_rl_env.sh` installs
   matching torch/vLLM nightlies; the rootfs pin (0.27.0) predates GLM support,
   but that only matters for the native-vLLM alternative.
5. **Weight sync**: TorchStore `put_state_dict` of the full policy each step
   (`torchtitan/rl/distributed/WEIGHT_SYNC.md`). Names are TorchTitan FQNs on
   both sides in the unified-model design, so no HF mapping is needed. With
   LoRA, the trainer would have to merge and push 584 GiB (BF16) per step
   unless an adapter-only sync is added. The native-vLLM alternative needs
   `to_hf` names plus vLLM's fused mappings (`in_proj_qkvbfg_a`,
   `fused_qkv_a_proj`, `wk_weights_proj`, `gate_up_proj`;
   `vLLM:common/model.py:860-877`). vLLM LoRA for this model is still an
   unmerged PR ([#56327](https://github.com/vllm-project/vllm/pull/56327)).
6. **RL parity hazards specific to GLM**: vLLM's indexer scores in FP8 after a
   Hadamard rotation while a BF16 trainer scores in bf16, so token selections
   can differ near the top-k boundary. Z.ai found that non-deterministic top-k
   alone caused entropy collapse (GLM-5 report, Section 3.2). The trainer
   should either reuse the generator's selections or match the FP8 indexer
   numerics, and use deterministic `torch.topk`.

## 7. Ordered tracer-bullet plan

Each step has a gate; do not start the next one until the gate passes.

1. **Stage the checkpoint to HDFS.** On a host with >= 650 GB free (here

## 8. Open questions

1. **Text-only or multimodal SFT?** The model is natively multimodal; the plan
   above is text-only. Vision adds a 0.56B ViT and the processor contract.
2. **Context length target.** 8k fits on 4x; 32k needs 8x or new FP8/CP work.
   This decides whether step 6 is needed at all.
3. **4x vs 8x for SFT.** On 4x with BF16 there is no headroom; is 8x
   acceptable for the first SFT run?
4. **BF16 for LoRA params and optimizer** (global `training.dtype`), or invest
   in per-FQN dtype so LoRA and Adam stay fp32 and the F32 checkpoint tensors
   stay F32?
5. **LoRA targets.** Attention + shared experts only (cheap), or also routed
   experts (+26.6 GiB total)? Should MLA `kv_b` (the absorbed W_UK/W_UV) be
   targeted?
6. **Indexer during SFT.** Frozen is assumed (matches HF and the RL recipe);
   the GLM-5 report is silent on SFT.
7. **RL architecture.** TitanRL unified model (more work, bitwise-parity
   tooling) vs native vLLM generator (less work, FP8 indexer mismatch,
   HF-name sync). How many GPUs can RL use (>= 12 B200 for BF16 trainer + FP8
   generator)?
8. **HDFS direct read.** The HF loader cannot read `hdfs://`. Is a local NVMe
   staging cache per node acceptable (598 GiB BF16 per node), or should a
   waystone-backed `StorageReader` wrapper be built?
9. **tinker hosted availability** for GLM-5.3-Flash LoRA, and whether data may
   leave the cluster.
10. **DSv4 `HcPost` axis** (Section 3.4): confirm against the DeepSeek-V4
    reference. If it is a bug, DSv4 numerics in this checkout change.
11. **Unverified sources:** the vLLM tweet text (unreachable), the SGLang
    implementation (not read line by line), and the exact first vLLM release
    containing GLM-5.3-Flash (recipe says 0.29.0+; raw-path probe found it at
    v0.30.0).
