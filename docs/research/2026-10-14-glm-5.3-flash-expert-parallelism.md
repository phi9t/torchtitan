# GLM-5.3-Flash Expert Parallelism Deep Dive

Date: 2026-10-14

## Scope and source quality

This note is a phase-1 design analysis for adding true expert parallelism (EP)
to the repo-local GLM-5.3-Flash experiment. It does not change model code and
does not claim GPU training evidence. The concrete question is whether
TorchTitan's existing MoE EP machinery can reduce GLM's routed-expert memory and
load-time pressure on 8x and 4x B200 runs, and what phase-2 work should prove
before landing such a change.

## Headline

EP is a useful GLM phase-2 direction, but it is not a standalone 4-GPU memory
solution.

For the same world size, EP does not reduce the steady BF16 frozen-base static
shard: 8 GPUs still start near 73.05 GiB/GPU and 4 GPUs still start near
146.09 GiB/GPU under the current LoRA-rank-16 memory plan
(`.scratch/glm53-flash-sft-ladder/evidence/t07b/full_size_param_counts.json:165-194`).
What EP reduces is the routed-expert ownership and unshard unit. On 4 GPUs,
moving from EP=1 to EP=4 cuts the largest routed MoE all-gather component from
about 13.81 GiB to about 3.38 GiB, but the resulting static-plus-largest-unshard
estimate is still about 149.47 GiB/GPU before activations, NCCL, allocator
fragmentation, dataloader, checkpointing, Dist-MoE scratch, or KDA/Triton
workspace.

That matters because the prior 8-GPU GLM LoRA smoke run measured 72.99 GiB model
CUDA memory before training and 131.56 GiB peak for one optimizer step
(`.scratch/glm53-flash-sft-ladder/sdd/task-08b-report.md:153-180`). The 4-GPU
problem statement already framed the BF16 frozen base as 145.9 GiB/GPU and the
8-GPU peak as 72.99 GiB static plus about 58.6 GiB other memory
(`.scratch/glm53-flash-sft-ladder/sdd/task-09-common.md:7-9`). EP can shrink a
large transient and make rank-local expert loading cheaper, but a 4-GPU full
loop still needs a second memory direction, such as offload or a stored-quantized
frozen base, unless phase-2 measurements show the non-static stack is far lower
than T08b's one-step evidence.

## 1. TorchTitan EP Today

### Mesh axes

TorchTitan has an `ep` mesh axis for expert ownership and an `edp_shard` axis
for leftover sparse FSDP; there is no separate `etp` axis in this checkout. The
parallelism context documents `ep` as `expert_parallel_degree` and derives
`edp_shard = dp_shard * cp * tp // ep`
(`torchtitan/distributed/PARALLELISM_CONTEXT.md:17-18`). EP is not a new factor
in the world-size product; it reuses ranks already covered by
`dp_replicate * dp_shard * cp * tp * pp == world_size`
(`torchtitan/distributed/PARALLELISM_CONTEXT.md:23-33`). The valid carving rule
is:

```text
ep must divide (dp_shard * cp * tp)
dp_shard * cp * tp == edp_shard * ep
```

That rule is explicit in the mesh note
(`torchtitan/distributed/PARALLELISM_CONTEXT.md:35-56`). Dense modules stay on
the dense mesh, while routed experts use the sparse mesh with expert weights
`Shard(0)` on `ep` and leftover FSDP on `edp_shard`
(`torchtitan/distributed/PARALLELISM_CONTEXT.md:53-56`).

For current GLM this is constraining: the GLM experiment validation rejects TP,
CP, and PP, while only checking expert divisibility
(`torchtitan/experiments/glm53_flash/sharding.py:20-48`). With
`tp=cp=pp=1`, an 8-GPU run can choose EP in `{1, 2, 4, 8}`, but a 4-GPU run can
choose only `{1, 2, 4}`. EP=8 on 4 GPUs would require GLM to support TP or CP
inside `dp_shard * cp * tp`, not just a config flip.

### Runtime flow

The common `MoE` forward contract is router -> routed experts -> shared experts
-> sum. Its docstring states that with EP, the token dispatcher performs
all-to-all communication to send routed tokens to expert-owning ranks, and the
combine path performs the reverse all-to-all before the score-weighted
scatter-add (`torchtitan/models/common/moe.py:636-653`). The common wrapper also
owns the TP token-sharding transitions for the routed branch: when EP is active,
routed tokens are consumed as `Shard(0)` across the dense TP group, and the
padding mask is sharded to match (`torchtitan/models/common/moe.py:718-727` and
`torchtitan/models/common/moe.py:756-795`). If dense sequence parallelism is not
enabled, the routed output is zero-filled into a TP partial and one final
all-reduce materializes the MoE output
(`torchtitan/models/common/moe.py:797-847`).

The all-to-all dispatcher resolves the active one-dimensional EP mesh from the
ambient sparse SPMD runtime (`torchtitan/models/common/token_dispatcher.py:196-203`).
Its `AllToAllTokenDispatcher` owns dispatch and combine remat regions, token
count exchange, and the variable-size data all-to-all
(`torchtitan/models/common/token_dispatcher.py:235-330`). This is dropless
token-choice routing in the base path: the source code exchanges real
per-expert token counts and moves the routed token payload; it is not a
capacity-dropping router.

### Parameter placement and FSDP

The common sparse expert placement puts routed-expert weights on `Shard(0)` of
the expert dimension when EP is enabled
(`torchtitan/models/common/moe_sharding.py:43-61`). The same sharding file
states that MoE reuses the dense `tp` mesh axis for routed token sharding under
EP and that token count buffers are partial across DP, CP, and TP
(`torchtitan/models/common/moe_sharding.py:64-79`). The MoE sharding guide
summarizes the two supported EP layouts: routed experts use the sparse
`ep`/`edp_shard` mesh, routed expert weights are `Shard(0)` on EP, and routed
input/output are either sequence-sharded with SP or converted through a partial
when SP is off (`torchtitan/models/common/MOE_SHARDING.md:18-29`).

`set_routed_moe_sharding_config` wires this into an `MoE.Config`: wrapper,
router, router gate, and routed experts all get explicit sharding configs, and
the routed expert `w13`/`w2` grouped linears use sparse expert placements when
EP is enabled (`torchtitan/models/common/moe_sharding.py:217-245`).
`make_routed_experts_config` builds the standard grouped expert modules with a
`GroupedLinear` `w13` shape for gate/up, a `GroupedLinear` `w2` shape for down,
and an `AllToAllTokenDispatcher`
(`torchtitan/models/common/config_utils.py:371-404`). `make_moe_config` then
packages router, routed experts, shared experts, and optional load-balancing
loss (`torchtitan/models/common/config_utils.py:317-338`).

FSDP has a matching sparse path. `resolve_sparse_fsdp_mesh` returns the sparse
storage mesh when EP is enabled and uses `edp_shard` as the FSDP shard axis
(`torchtitan/distributed/fsdp.py:112-126`). In MoE blocks, FSDP switches
per-parameter mesh ownership: routed expert parameters use the sparse
`edp_mesh`, while non-expert parameters use the dense `dp_mesh`
(`torchtitan/distributed/fsdp.py:331-425`). Generic config validation enforces
that MoE EP is at least TP, that the number of experts is divisible by EP, and
that routed-expert sharding agrees with `expert_parallel_degree`
(`torchtitan/config/validation.py:87-123`).

### Existing model precedents

Qwen3 builds MoE blocks directly from `make_moe_config`,
`make_router_config`, and `make_routed_experts_config`
(`torchtitan/models/qwen3/flavors.py:144-182`), then resolves sharding from
`parallelism.expert_parallel_degree > 1`
(`torchtitan/models/qwen3/model.py:139-146`). DeepSeek V3 and V4 follow the
same top-level pattern:
`set_deepseek_v3_sharding_config(... enable_ep=parallelism.expert_parallel_degree > 1)`
and
`set_deepseek_v4_sharding_config(... enable_ep=parallelism.expert_parallel_degree > 1)`
(`torchtitan/models/deepseek_v3/model.py:290-297`,
`torchtitan/models/deepseek_v4/model.py:239-246`).

Kimi K3 is the best GLM precedent because it keeps the common MoE wrapper but
adds model-specific logic around the routed path. `KimiLatentMoE` subclasses the
common `MoE`, calls the common router and routed experts, and preserves the
same routed-branch TP transitions and output combine helpers
(`torchtitan/models/kimi_k3/moe.py:23-102`). Its sharding code first calls the
core MoE plan, then adds sharding for Kimi-specific latent projections around
the routed experts (`torchtitan/models/kimi_k3/sharding.py:220-248`). GLM's EP
implementation should follow that extension pattern instead of copying common
MoE machinery into the experiment.

### Dist-MoE boundary

The `dist_moe` package is not required for the first GLM EP implementation. It
is a more specialized backend that owns dispatch, grouped expert computation,
activation storage, and scratch storage. Its README says TorchTitan supports
BF16 and asynchronous MXFP8 Dist-MoE training on NVIDIA SM100 or newer
(`torchtitan/models/common/dist_moe/README.md:6-10`), and the runtime enforces
an SM100-or-newer CUDA device (`torchtitan/models/common/dist_moe/runtime.py:304`).
The runtime's config includes scratch and optional VMM overflow capacity factors
(`torchtitan/models/common/dist_moe/runtime.py:187-218`), while
`DistMoeRoutedExperts` consumes ordinary grouped TorchTitan weights but bypasses
their `forward` methods for dispatch, SwiGLU, expert GEMMs, and combine
(`torchtitan/models/common/dist_moe/routed_experts.py:32-39`). The MXFP8
variant preserves the inherited W13/W2 parameter and checkpoint layout while
preparing grouped qdata/scale operands for each FSDP unshard lifetime
(`torchtitan/models/common/dist_moe/mxfp8.py:109-146`). For GLM, this belongs
in a later GPU performance ticket after ordinary all-to-all EP proves numerical
parity and loader/checkpoint correctness.

## 2. What GLM Needs To Plug In

### Current GLM layout

The GLM experiment already stores routed experts in grouped tensors that are
close to the common grouped-linears contract. `GlmExperts` owns:

- `gate_up_proj` with shape `(num_experts, 2 * moe_intermediate_size, hidden)`;
- `down_proj` with shape `(num_experts, hidden, moe_intermediate_size)`.

Those parameters are defined in
`torchtitan/experiments/glm53_flash/model.py:254-270`. Its forward path loops
over active experts locally, applies the fused gate/up projection, clamps GLM's
SwiGLU inputs, applies down projection, weights top-k contributions, and
`index_add_` combines into token order
(`torchtitan/experiments/glm53_flash/model.py:272-295`). The router is a
sigmoid top-k router with a persistent correction bias
(`torchtitan/experiments/glm53_flash/model.py:298-325`). `GlmMoE` combines that
routed path with a shared expert MLP
(`torchtitan/experiments/glm53_flash/model.py:328-350`).

The current model parallelization path applies local compile, optional activation
checkpointing, and FSDP only
(`torchtitan/experiments/glm53_flash/model.py:1205-1224`). Its FSDP helper
already passes `ep_degree=parallelism_context.ep` and an `edp_mesh` from
`resolve_sparse_fsdp_mesh` into `apply_fsdp_to_decoder`
(`torchtitan/experiments/glm53_flash/model.py:1311-1337`), but the experiment
validation explicitly says this seam does not implement token-dispatch EP
execution, TP, or CP for sparse MLA
(`torchtitan/experiments/glm53_flash/sharding.py:20-26`). So today GLM can
benefit from the sparse FSDP mesh only insofar as the grouped expert parameters
are recognized as routed experts; it does not yet have common-MoE dispatch and
combine.

### Recommended module shape

The lowest-risk GLM EP shape is an experiment-owned adapter around common MoE:

1. Keep GLM attention, KDA, sparse MLA, hyper-connections, shared experts, and
   public config in the existing experiment seam.
2. Replace only the routed MoE block implementation with a GLM-specific
   `MoE`-compatible config/module that uses common router/dispatcher/expert
   placement but preserves GLM semantics:
   sigmoid routing, correction bias, `norm_topk_prob`, `routed_scaling_factor`,
   top-8 over 288 experts, clamp-limited SwiGLU, and one shared expert.
3. Prefer common `GroupedLinear` storage for `w13`/`w2` if it can preserve the
   existing native keys or provide a small state-dict adapter. GLM's current
   `gate_up_proj` and `down_proj` shapes map directly onto common routed expert
   weights; the major compatibility issue is naming, not mathematical layout.
4. Use the common sharding function for the MoE wrapper and routed experts, then
   add only GLM-specific sharding around any wrappers, following the Kimi K3
   pattern.

This should live either as a new experiment package such as
`torchtitan/experiments/glm53_flash_ep/` for phase-2 isolation or as a proposed
change to `torchtitan/experiments/glm53_flash/` once T08d ownership is clear.
It should not require edits to `torchtitan/models/common/` for the first proof.

### LoRA under EP

The task brief says to inspect expert LoRA. The checked-in GLM LoRA target list
currently includes attention projections and shared experts, not routed experts:
`shared_experts.{gate,up,down}_proj` are present, but `experts.gate_up_proj` and
`experts.down_proj` are not
(`torchtitan/experiments/glm53_flash/flavors.py:214-230`). The T07b evidence
matches that: rank-16 LoRA adds 54,804,480 sparse-attention parameters and
12,386,304 shared-expert parameters, with no routed-expert LoRA bucket
(`.scratch/glm53-flash-sft-ladder/evidence/t07b/full_size_param_counts.json:144-147`).

For the current checked-in LoRA policy, GLM EP only needs to keep shared-expert
LoRA on the dense/shared-expert path and preserve trainable-only checkpoint
filtering. If routed-expert LoRA is added later, its adapters must follow the
same expert-axis placement as the base grouped expert weight. Common grouped
LoRA already encodes that rule: for grouped adapters, both LoRA A and B inherit
the base grouped projection placement, and the accepted placements include
`expert_param_placement_sparse()`
(`torchtitan/models/common/lora.py:148-169`). Phase-2 should test both the
current shared-expert LoRA policy and an optional routed-expert LoRA policy if
the target list is expanded.

For scale: rank-16 LoRA on all routed GLM experts would add a hypothetical
3,567,255,552 trainable parameters across 42 MoE layers. With BF16 params,
BF16 grads, and 8 bytes of Adam state per parameter, that is about 39.87 GiB
total optimizer/grad/static adapter state: 9.97 GiB/GPU on 4 GPUs or
4.98 GiB/GPU on 8 GPUs if sharded only by world size. This is not the current
checked-in configuration; it is a warning for any phase-2 expansion of LoRA
targets.

### Router stats and load balancing

Common MoE has a load-balancing hook that iterates MoE layers and updates expert
biases from router token-count buffers before optimizer steps
(`torchtitan/models/common/moe.py:873-906`). GLM already has an
`e_score_correction_bias` buffer in the router
(`torchtitan/experiments/glm53_flash/model.py:306-311`), matching the released
router contract more closely than the common auxiliary-loss-free bias update.
Phase-2 should not silently swap GLM's correction-bias behavior for the common
load-balance hook. Instead, record router stats under EP first:

- per-layer, per-rank `tokens_per_expert`;
- top-k mass and zero-token experts;
- max/min/mean routed rows per local expert;
- all-to-all input/output split histograms;
- Countdown-specific skew by problem type or prompt length.

The first parity ticket can set common `load_balance_coeff=None` and preserve
GLM's existing correction-bias state unchanged. Any dynamic bias update or aux
loss belongs in a separate numerical-change ticket.

### State dict and rank-local loader

The existing GLM rank-local HF loader is already close to EP-ready. It iterates
live parameters and buffers after FSDP, skips LoRA tensors, computes DTensor
local shape and global offset, and reads only the needed HF safetensors slices
(`torchtitan/experiments/glm53_flash/sharded_hf_load.py:91-138`). For grouped
experts, it maps local expert offsets to per-expert HF keys:
`_copy_grouped_down` loops from `target.global_offset[0]` over local experts and
reads only those experts' `down_proj.weight` slices
(`torchtitan/experiments/glm53_flash/sharded_hf_load.py:278-301`), while
`_copy_gate_or_up_rows` does the same for `gate_proj` and `up_proj`
(`torchtitan/experiments/glm53_flash/sharded_hf_load.py:304-342`).

The state-dict adapter has the same local-expert concept for export. When a
grouped expert tensor is a DTensor, it records the grouped expert DTensor,
uses `local_experts_indices`, and exports only the local expert IDs for
gate/up/down HF keys
(`torchtitan/experiments/glm53_flash/state_dict_adapter.py:78-123`). If phase-2
turns routed experts into true EP `Shard(0)` tensors, this machinery should
naturally read and write only each EP rank's expert IDs. The main work is
preserving or mapping native key names if `GlmExperts` is replaced by common
`RoutedExperts`.

The load-time win is meaningful. T08b loaded 78,331,751,136 local bytes on an
8-GPU FSDP-only smoke run and skipped LoRA tensors
(`.scratch/glm53-flash-sft-ladder/sdd/task-08b-report.md:153-170`). With true
EP, routed expert HF reads should scale with local experts: 144 experts/rank at
EP=2, 72 at EP=4, and 36 at EP=8, instead of every rank touching all 288
experts within the largest all-gather lifetime.

## 3. Memory And Communication Model

### Inputs and assumptions

GLM full-size constants used here:

- hidden size 4096;
- 45 decoder layers;
- first 3 dense layers, 42 MoE layers;
- 288 routed experts;
- top-k 8;
- one shared expert;
- MoE intermediate size 2048;
- T08b training target: sequence length 512, 32,768 tokens per optimizer step,
  94 configured steps, seed 42.

Counts come from T07b:

- base total params: 313,326,799,870;
- routed expert params: 304,405,807,104;
- non-routed base params: 8,920,992,766;
- current rank-16 LoRA adapter params: 67,190,784;
- largest current FSDP unit layer params: 7,414,112,502;
- largest current BF16 all-gather: 13.8098606877 GiB;
- 8-GPU static floor: 73.0459449287 GiB;
- 4-GPU static floor: 146.0918898573 GiB
  (`.scratch/glm53-flash-sft-ladder/evidence/t07b/full_size_param_counts.json:1-198`).

The memory table assumes:

- BF16 frozen base, 2 bytes per parameter;
- current checked-in rank-16 LoRA policy, not hypothetical routed-expert LoRA;
- same world size and no offload or quantization;
- EP only changes routed expert ownership/unshard size;
- dense parameters, shared experts, router, KDA, sparse MLA, embeddings, LoRA
  state, activations, NCCL, optimizer workspaces, allocator fragmentation,
  dataloader, checkpointing, and Dist-MoE scratch are not reduced by this EP
  table unless explicitly shown.

`edp` is `dp_shard * cp * tp / ep`; with current GLM constraints this is simply
`world_size / ep`.

| 8 | 1 | 8 | 288 | 72.952 | 0.094 | 73.046 | 13.810 | 86.856 | yes |
| 8 | 2 | 4 | 144 | 72.952 | 0.094 | 73.046 | 6.750 | 79.796 | yes |
| 8 | 4 | 2 | 72 | 72.952 | 0.094 | 73.046 | 3.375 | 76.421 | yes |

The largest routed MoE layer base weight is 7,247,757,312 params, or 13.500 GiB
BF16. At EP=4, only 72 of 288 experts belong to each rank, so the routed part
of that unshard is about 3.375 GiB. This is lower than T07b's original 13.810
GiB full-layer all-gather, but it does not move the 146.092 GiB 4-GPU static
floor.

### All-to-all traffic estimate

Assumptions for the communication table:

- BF16 routed token payload only;
- balanced routing;
- no padding/capacity overhead;
- no router/count traffic;
- no Dist-MoE scratch or alternate kernels;
- dispatch plus combine for forward;
- training approximation doubles that aggregate to account for backward payload
  movement at the same scale.

Per MoE layer forward aggregate all-to-all payload:

```text
2 * tokens_per_step * top_k * hidden_size * 2 bytes * (EP - 1) / EP
```

Across 42 MoE layers:

| EP | Forward aggregate at 512 tokens GiB | Approx training aggregate at 512 tokens GiB | Forward aggregate at 32,768 tokens GiB | Approx training aggregate at 32,768 tokens GiB |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 0.000 | 0.000 | 0.000 | 0.000 |
| 2 | 1.312 | 2.625 | 84.000 | 168.000 |
| 4 | 1.969 | 3.938 | 126.000 | 252.000 |
| 8 | 2.297 | 4.594 | 147.000 | 294.000 |

At 32,768 tokens/step, the aggregate share per GPU is:

| World | EP | Forward GiB/GPU | Approx training GiB/GPU |
| ---: | ---: | ---: | ---: |
| 8 | 2 | 10.500 | 21.000 |
| 8 | 4 | 15.750 | 31.500 |
| 8 | 8 | 18.375 | 36.750 |
| 4 | 2 | 21.000 | 42.000 |
| 4 | 4 | 31.500 | 63.000 |

So EP trades memory and load locality for communication. On 8 GPUs that trade is
likely worthwhile because static memory is comfortable. On 4 GPUs, EP=4 is the
only valid maximum in the current seam and would add about 63 GiB/GPU of
training all-to-all payload per optimizer step at T08b token count. That is not
automatically disqualifying on NVLink-class B200 nodes, but it must be measured
with at least 10 warm steady steps; one-step smoke throughput is not performance
evidence.

## 4. Feasibility Against T09

T09's 4-GPU problem was not just the largest all-gather. It was the combination
of a 145.9 GiB/GPU BF16 frozen base with non-static memory observed in the
8-GPU smoke run (`.scratch/glm53-flash-sft-ladder/sdd/task-09-common.md:7-9`).
EP attacks one high-value part:

- 4-GPU EP=4 lowers the largest routed unshard estimate by about 10.43 GiB/GPU
  versus EP=1.
- It should reduce grouped expert HF read bytes and load-time scratch because
  each rank touches 72 routed experts instead of 288.
- It preserves BF16 base storage and does not require quantization or offload by
  itself.

But even the optimistic static-plus-largest-unshard number remains 149.47 GiB.
On a nominal 178 GiB B200 that leaves only about 28.5 GiB before activations,
Triton/KDA workspace, NCCL, CUDA graph or compiler allocations, optimizer
metadata, fragmentation, dataloader, and checkpointing. The T08b one-step probe
had about 58.6 GiB of non-static memory over the 8-GPU static model component,
so EP alone is unlikely to make the 4-GPU full loop pass without further memory
work.

Recommended positioning:

- On 8 GPUs, EP is a performance/load-memory improvement and a prerequisite for
  clean large-MoE scaling.
- On 4 GPUs, EP is a supporting direction that should be paired with another
  memory direction from the T09 ladder. It can reduce the largest full-layer
  unshard and loader pressure, but it does not replace offload or
  frozen-base quantization evidence.

## 5. Risks

**Dropless skew.** The common all-to-all dispatcher moves real routed tokens and
does not drop by capacity in the base path. Countdown prompts may route
unevenly, especially with top-8 over 288 experts. EP=8 on 8 GPUs means only 36
experts per rank; EP=4 on 4 GPUs means 72 experts per rank. Phase-2 must record
split histograms and max local routed rows per expert, not only average tokens.

**Router semantics.** GLM's sigmoid router, correction bias, normalized top-k
probability, and route scaling are part of the checkpoint contract. The first EP
patch should preserve them and disable any unrelated common bias-update behavior
unless a separate numerical-change ticket proves equivalence.

**Determinism and resume.** All-to-all can change token grouping, grouped GEMM
order, rematerialization boundaries, and floating-point accumulation order.
Phase-2 parity must use the truncated-depth full-width config, fixed seed, fixed
data, deterministic mode where supported, and compare full-precision losses and
grad norms. A rounded console loss is not enough. Resume parity must include
model, optimizer, scheduler, dataloader, RNG, router buffers, and train-step
state.

**Checkpoint and key compatibility.** Replacing `GlmExperts` with common
`RoutedExperts` risks changing native keys (`gate_up_proj`/`down_proj` versus
`routed_experts.w13.weight`/`w2.weight`). The rank-local loader and adapter
already know how to load grouped expert slices by local expert ID, but phase-2
must keep old checkpoint load/export behavior or document a migration.

**LoRA placement.** Current checked-in GLM LoRA does not target routed experts.
If phase-2 adds routed-expert LoRA, grouped adapter weights must be placed on
the expert axis with their base weights, and trainable-only checkpoint filtering
must include those new keys.

**KDA, sparse MLA, and MTP.** EP touches only MoE layers. No direct interaction
with GLM KDA or sparse MLA math is expected. However, TP or CP support would be
needed for EP=8 on 4 GPUs, and that would interact with sparse MLA/KDA tensor
layouts. MTP is outside the current GLM experiment path and should not be
quietly pulled into the EP proof.

**Dist-MoE runtime.** Dist-MoE brings SM100 CUDA requirements, scratch/VMM
planning, and optional MXFP8 prepared weights. It should be measured after plain
all-to-all EP works; otherwise kernel/runtime questions can mask basic
state-dict, loader, and numerical-parity failures.

## 7. Recommendation

Proceed with a phase-2 isolated EP prototype, but do not market it as the 4-GPU
answer by itself. The useful first-order benefits are:

- smaller routed expert unshard units;
- rank-local expert HF reads;
- a path toward real large-MoE scaling and later Dist-MoE kernels.

The hard limits are:

- EP does not reduce the BF16 frozen-base static floor for the same world size;
- 4-GPU EP=8 is invalid until GLM supports TP or CP;
- all-to-all traffic becomes a first-class performance concern;
- current LoRA targets do not include routed experts, so any routed-expert LoRA
  memory and placement story is a separate extension.

After T12, the next ticket should be EP-4/T13: prove truncated-depth,
full-width numerical behavior against the FSDP-only GLM path before spending
full-depth GPU budget.
